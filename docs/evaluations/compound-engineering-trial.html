Worked example: inputs, method, answer

The input is deferred-trial.json. It has an unresolved plugin revision and no observed criteria. From the repository root:

uv run --no-project python scripts/evaluation/compound_trial.py \
  examples/compound-engineering/deferred-trial.json --root .

The method validates the record structure, classifies each named criterion, and checks any referenced evidence bytes. Hand enumeration of the input gives zero passing criteria, zero failed criteria, and five pending criteria. The following fields are extracted from the full JSON output:

{
  "counts": {"PASS": 0, "FAIL": 0, "NOT_EVALUATED": 5},
  "disposition": "defer",
  "ready_for_maintainer_review": false
}

The exit status is 1, the documented result for a valid record that does not establish readiness. Status 0 means all criteria pass and the evidence is ready for maintainer review; status 2 means an invalid record or unavailable evidence. No status authorizes adoption.

Record contract

The top-level keys are exactly schema_version (local format version 1), plugin, and criteria. The plugin object contains nonempty version text and revision, either null or a full lowercase Git commit ID. Each criterion contains exactly status, nonempty reason, and an evidence array. Status is one of PASS, FAIL, or NOT_EVALUATED.

Each evidence item contains exactly path and sha256. Paths use repository-relative forward slashes, remain within the selected root after symlink resolution, and identify regular files. Digests use lowercase hexadecimal. Repeated paths within a criterion, duplicate JSON keys, unsupported formats, missing criteria, and unknown fields are rejected. An observation with PASS or FAIL requires evidence; PASS also requires a pinned plugin revision. Any FAIL governs the disposition; otherwise any pending criterion defers readiness. The validator only reads the selected record and local artifacts.

Procedure for the live trial

  1. Resolve and record the intended plugin revision and manifest version. Verify user-scoped installation authority separately from repository write authority.
  2. Install and run setup in an isolated feature worktree. Record dependency health and before/after repository state. Confirm local configuration is ignored. Follow the worktree issue; never copy credentials into evidence.
  3. Run the advisory skills in report-only mode against a named revision. Classify useful findings and noise individually. Record elapsed time and judgment without inventing a numerical acceptance threshold.
  4. Run the complete plan/work/review/compound sequence on a bounded real task. Record protected-main checks and the resulting reusable knowledge. Evaluate the knowledge on the next occurrence before claiming a measured time saving.
  5. Retain public-ready observations and their digests, update the trial record, run the validator, and obtain independent review. Resolve the adoption decision in the decision issue; a complete record alone is not authorization.

Limitations and next checkpoint

Hashes establish agreement with recorded bytes, not the truth, completeness, authorship, or quality of an observation. The script does not query installation state, execute assistants, inspect remote checks, verify a plugin revision against upstream, or enforce repository policy. The sample record is a pending record, and the tests' passing records are synthetic. No engineering input data or licensed-source values are introduced. The next checkpoint is a permitted version-pinned installation and live trial, followed by independent review.
