Workflow API module analysis

Draft for maintainer review

1 Executive summary

The workflow application programming interface is an in-process execution and evidence interface. Analysis is performed to determine how a registered calculation is called and which evidence is returned; key results are summarized below.

  • Run the public CSV example through the typed interface.
    • The registered example returns 2 output files and equal output hashes on repetition. This equality is limited to the executed example and its current environment.
  • Inspect returned status and warnings before consuming output metadata.
    • Content hashing is distinguished from engineering acceptance. No physical acceptance limit is supplied by this interface.
  • Select explicit records when durable identity or publication is required.
    • The envelope alone does not freeze input-file bytes or enforce a clean source revision.

2 Purpose and system boundary

A workflow configuration is dispatched through the existing calculation engine. A result envelope is returned so that calling software is separated from command-line execution.

The main path is run_workflow. Registry resolution, configuration merging, temporary output discovery and hashing are provided by that path. Identity, input admission, artifact, output, metric and publication contracts are supplied as additional interfaces; they are not automatically applied by the runner. [4]

A physical geometry, mesh or structural boundary condition is not represented by this interface. Such inputs belong to the selected calculation and are outside this software diagram.

3 Basis and theory

Stored-byte identity is formed by hashing the bytes supplied to the artifact interface. The hash algorithm is specified externally; the composition of workflow records is specified by the implementation.

Stored bytes and canonical serialization

d = SHA-256(B)

B denotes the stored byte sequence and d its content digest. SHA-256 is specified by FIPS 180-4, August 2015, sections 5.1.1 and 6.2. Compression is descriptive metadata and is not decoded before hashing by the artifact interface. Hash equality is evidence of byte agreement under that digest, rather than a mathematical proof that collisions are impossible. [1] [4]

For the small integer objects used here, compact JSON punctuation and ordered keys are used. Whitespace, key sorting and UTF-8 generation are described in RFC 8785, June 2020, sections 3.2.1, 3.2.3 and 3.2.4. UTF-8 encoding for ASCII characters is specified in RFC 3629, November 2003, section 3. [2] [3]

The identity serializer differs from RFC 8785 for general data: Unicode normalization is applied, and decimal values are rendered without the RFC's required number conversion rules. RFC conformance is therefore not claimed. The ASCII integer examples do not exercise these differences. [2] [4]

Runner evidence and acceptance criteria

Runner input hashing serializes configuration after removing volatile top-level settings. Runner result hashing serializes the sorted output-name and file-digest pairs. These operations use the envelope serializer, separately from the identity serializer. Repeat equality means the result hashes from separate executions compare equal. The documented example is accepted here only when its status is ok, warnings are absent, and the opt-in repeat check returns true. These are software criteria, with no engineering capacity interpretation. [4] [4]

4 Inputs and outputs

A registered workflow identifier or a complete configuration dictionary is supplied by the caller. The returned envelope is inspected before downstream use.

Caller inputs

workflow_id selects a registry entry. params recursively overrides its loaded example configuration. cfg supplies a full configuration and takes precedence over registry example loading; in that branch, params is not merged. The workflow identifier still labels the envelope. verify_reproducible defaults to false; setting it to true requests a fresh repeat execution. Relative CSV paths in the documented example are resolved from the repository root. [4]

Envelope outputs

status is ok or error. A successful file result contains basenames, byte sizes and content digests. Provenance contains a best-effort code version, configuration hash, time and standards list; the runner does not populate engineering standards. Determinism contains the result hash and a repeat flag that is null unless requested. Confidence remains null. Warnings contain discovery discrepancies or caught error text. Unknown identifiers and caught exceptions return error envelopes. [4]

Only direct files in the resolved result directory are discovered. The saved configuration dump is excluded. Registry output names are documentary: their count is cross-checked when declared, but the actual filenames are used. An empty file list can accompany an ok status and a warning; status alone is insufficient. [4]

5 Worked public workflow example

The registered descriptive-statistics example is executed by calling the module. Its repository sample CSV groups are processed without a physical design interpretation.

from assetutilities.workflow_api import run_workflow

result = run_workflow("data_exploration", verify_reproducible=True)
assert result.status == "ok"
assert not result.warnings
assert result.determinism["reproducible"] is True
print(len(result.result["outputs"]))

The module returns 2 output files. Each declared input group generates its own statistics file; the saved configuration dump is omitted by the locator. The repeat flag is true because the separate executions return equal content-based result hashes. Output locations and basenames are recorded in section 9.2. [4]

Numeric statistics are not carried in the envelope: the returned payload lists output metadata. Access to the generated CSV values requires an output capture or persistence mechanism before temporary cleanup. No coefficient from the sample CSV files is interpreted as a physical performance limit.

6 Stored-byte worked anchors

Small byte sequences and structured objects are passed to the artifact constructors. The returned byte counts are checked against hand-counted punctuation and ASCII characters.

The stored ASCII sequence abc returns 3 bytes. The object {"a":1} returns 7 bytes. The object supplied as {"b":2,"a":1} is stored as {"a":1,"b":2} and returns 13 bytes. These byte counts are module outputs; their hand calculations are supplied with the report tests. [2] [3] [4]

7 Validation evidence

Existing tests are mapped to their software contracts. The map is a source inventory, rather than a statement of engineering accuracy or an executed test count.

The existing suite contains 113 test definitions in 9 files, counted from source before parameter expansion. Envelope round-tripping, hash sensitivity, registry merging, real engine execution, temporary-output isolation and opt-in repeat equality are exercised. Artifact tests cover byte integrity and storage-location binding. Identity and input tests cover explicit record membership and rejection of inadmissible inputs. [5]

Output and metric tests cover publication-surface restrictions, definitions and population eligibility. Publication tests use an in-memory port and a mocked external adapter. Those tests do not demonstrate live service access, credential configuration or successful external publication. No timing benchmark or field measurement is included in the cited workflow example. [5]

The report checks add literal hand-count anchors and consistency checks against fresh module calls. Counts are exact integers; floating point tolerances are unnecessary for the reported measurements. Only stable counts and names are embedded for the CSV example, so environment-sensitive CSV formatting and runtime timestamps are not presented as portable byte digests. [5]

8 Findings, limits and recommendations

Execution repeatability is demonstrated for the included example by the returned repeat flag. Durable input identity and physical acceptance remain separate responsibilities.

Limits of use

The runner configuration hash includes CSV path strings, rather than the referenced file bytes. Volatile top-level configuration settings are removed from that hash, even though changing a default setting can change execution. Provenance does not establish a clean source revision or an environment pin. Relative example paths require the repository context. The embedded engine path redirects ordinary outputs, but it is not a security sandbox for arbitrary configurations or plugins. [4]

The separate identity gate accepts caller-supplied cleanliness and revision evidence; it does not inspect the working tree itself. Its serializer is not general RFC 8785 conformance evidence. The architecture contract referred to by module docstrings is absent from the current checkout; implementation and tests are the available local contract evidence. [4]

Recommendations

Inspect status, warnings and expected outputs together, and request the repeat check for calculations that need repeat evidence. Materialize referenced input bytes and record explicit schema and environment evidence before using the separate identity and publication contracts. Capture output bytes before cleanup when persistent results are required. Test non-ASCII and decimal interoperability before exchanging canonical records with other implementations. These actions address the implementation boundaries described above. [4] [4] [2]

Supply the selected engineering method, input units, acceptance criteria and method-specific validation before treating a successful software status as acceptance of a physical design. No safety factor, capacity threshold or operating envelope is supplied or inferred by this report.

Not covered

Live publication, promotion recovery, metric population design, external credentials and the other registered engine routes are inventoried through tests but are not worked examples here. No external publication is performed.
